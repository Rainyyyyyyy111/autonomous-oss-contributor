## 每次怎么留档

1. 每个独立改动批次建立一份[变更记录](templates/change-record.md)，文件命名为 `changes/YYYY-MM-DD-NNN-short-name.md`。记录问题、修改前后行为、影响节点、实际验证、风险、回滚方式和待观察指标。一次聊天可能包含多个批次，多个提交也可以归为一个批次。
2. 同时更新本目录的[变更索引](CHANGELOG.md)和项目根目录的 [CHANGELOG](../../CHANGELOG.md)。在提交或 PR 中引用记录 ID。
3. 自动化步骤、状态转换、质量门槛、权限、预算、默认筛选规则或反馈触发条件变化时，建立下一份流程目录（如 `v0.2/`），列出相对上一版的变化。只影响实现、文案或缺陷修复且不改变流程契约时，继续关联当前版本。
4. 更新版本索引中的当前版本及两个 README 的入口。旧版本图、规则和记录保留；发现历史文档错误时，追加勘误并说明日期与原因。
5. 每个基线用 Git 提交保存实现与文档，以 `workflow-v0.1` 这样的标签定位；提交哈希以 Git 为准，避免在被引用的同一提交中填写自身哈希。软件发布继续使用独立的软件版本标签。

归档是研发记录，不增加运行时的逐 Issue 人工审批。文档与实际行为不一致时，先查对应代码、提交与实际验证证据，再记录修正。

## 分析约定

比较两个版本时使用相同的指标定义，保留分母、统计窗口与配置差异。至少分开记录：候选数、实际开工数、独立验证通过数、新 PR 数、合并数、未合并关闭数、仍开放数、模型时间和人工介入次数。详见 [v0.1 指标口径](v0.1/README.md#分析口径)。

SQLite/JSONL 和任务证据是具体运行记录；本目录是产品流程与变更档案。提交示例应使用合成或脱敏证据，不提交个人配置、数据库、认证、原始聊天和第三方仓库归档。
